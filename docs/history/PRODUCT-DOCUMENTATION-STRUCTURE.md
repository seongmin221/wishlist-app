# 제품 기획 문서 구조 설계

> 상태: **확정** · 날짜: 2026-09-10 · 영역: **문서 구조**

## 맥락

현재 제품 기획은 `docs/product-spec.md`와 `docs/history/PRODUCT-*` 문서에 분산돼 있다. `product-spec.md`는 제품 개요부터 세부 상태·예외 규칙까지 한 파일에 담고 있으며, `history` 루트에는 현재도 유효한 결정, 대체된 체크포인트, 진행 중이던 방향 문서가 함께 놓여 있다.

이 구조에서는 현재 유효한 최종 기획과 과거 판단 근거를 구분하기 어렵다. 날짜와 문서 종류를 알아야 원하는 내용을 찾을 수 있고, 하나의 사용자 흐름을 이해하기 위해 여러 결정 문서를 오가야 한다.

## 목표

- 현재 유효한 제품 기획을 사용자 목표와 흐름에 따라 찾을 수 있게 한다.
- 사람과 AI 에이전트가 같은 문서를 기준으로 제품 의도, 정상 흐름, 상태, 예외를 이해하게 한다.
- 현재 규칙과 과거 판단 근거의 역할을 분리한다.
- 출시 범위가 확장돼도 빈 미래 문서나 날짜 기반 파일을 만들지 않고 자연스럽게 확장할 수 있게 한다.
- 기존 history 내용과 Git 이력, 사용자가 작성 중인 변경을 보존한다.

## 범위 밖

- 아직 구체화되지 않은 V1·V2 기능의 상세 문서를 미리 만들지 않는다.
- API, 데이터베이스, 플랫폼별 구현 상세를 제품 문서에 복제하지 않는다.
- 과거 결정 문서를 현재 규칙처럼 다시 작성하지 않는다.
- 이번 설계에서 제품 규칙 자체를 새로 결정하지 않는다.

## 문서 우선순위

문서 내용이 충돌할 때는 다음 순서로 현재 기준을 판단한다.

1. `docs/product/`: 현재 유효한 제품 규칙
2. `docs/architecture/`: 제품 규칙을 구현하는 기술 설계
3. `docs/history/`: 결정 당시의 근거와 변화 과정
4. `docs/learning/`: 개념 설명과 프로젝트 학습 기록

과거 결정이 대체되면 history 본문을 현재 내용으로 고치지 않는다. 상태, 대체 관계, 현재 product 문서 링크를 추가해 원래 맥락을 보존한다.

## 목표 구조

```text
docs/
├── product/
│   ├── INDEX.md
│   ├── README.md
│   ├── overview.md
│   ├── save-a-product.md
│   ├── organize-candidates.md
│   ├── inspect-and-edit-a-product.md
│   ├── finish-a-purchase-decision.md
│   └── references/
│       ├── INDEX.md
│       ├── item-states.md
│       └── product-taxonomy.md
└── history/
    ├── INDEX.md
    ├── README.md
    ├── product-planning/
    │   ├── INDEX.md
    │   └── mvp/
    │       ├── INDEX.md
    │       ├── checkpoints/
    │       │   ├── INDEX.md
    │       │   ├── initial-direction.md
    │       │   ├── purpose-review.md
    │       │   ├── taxonomy-and-purpose.md
    │       │   └── policy-completion.md
    │       └── decisions/
    │           ├── INDEX.md
    │           ├── purpose-deletion.md
    │           └── duplicate-items.md
    └── architecture/
        ├── INDEX.md
        ├── repository/
        ├── client/
        ├── server/
        └── ai/
```

여러 문서나 하위 주제를 가진 폴더에는 간결한 `INDEX.md`를 둔다. `README.md`는 문서의 역할과 작성 규칙을 설명하고, `INDEX.md`는 탐색 경로와 현재 문서 목록을 제공한다.

## 현재 제품 문서의 책임

### `product/overview.md`

기존 `product-spec.md`를 간결한 제품 진입점으로 재구성한다.

- 제품 목적과 핵심 원칙
- MVP 포함·제외 범위
- 전체 사용자 여정
- 현재 상세 product 문서 링크
- 아직 구체화되지 않은 향후 범위
- 제품 수준의 미결정 사항

상세 기능 규칙은 반복하지 않는다. 미래 기능은 구체적인 기획이 시작되기 전까지 이 문서의 `향후 범위`에만 유지한다.

### `product/save-a-product.md`

상품 URL을 공유한 시점부터 서버 분석이 완료되거나 사용자가 실패에서 복구할 때까지를 소유한다.

- 시스템 공유 수신과 로컬 우선 저장
- 로그인·오프라인 상태의 대기와 계정 귀속
- 서버 전송과 분석
- Product 캐시 재사용과 WishlistItem 생성 경계
- 분석 실패, 재시도, 직접 보완 흐름으로의 인계
- 저장 중 삭제와 늦게 도착한 결과 처리

### `product/organize-candidates.md`

저장된 상품을 비교 가능한 후보로 분류하고 목적에 묶는 흐름을 소유한다.

- 공용·사용자 전용 카테고리
- 목적 생성·연결·해제·삭제
- AI 카테고리 분류와 목적 연결
- `분류·목적 확인`과 확정·보류
- 중복 후보 비교와 정리
- 카테고리·목적 변경이 활성 상품과 아카이브에 미치는 영향

중복 탐지는 저장 과정에서 시작될 수 있지만, 사용자 선택을 포함한 상세 규칙은 이 문서가 소유한다. 저장 문서는 이 흐름으로 연결만 한다.

### `product/inspect-and-edit-a-product.md`

상품을 목록에서 확인하고 세부 정보를 보완·수정하는 흐름을 소유한다.

- 홈 조치 필요 영역과 일반 목록의 노출 규칙
- 상품 정보 완료 기준
- 제품명, 이미지, 카테고리, 목적 편집
- 모든 처리 상태에서의 원본 링크 접근
- 앱 내 웹뷰 탐색과 외부 앱 이동
- 활성 상품 삭제

### `product/finish-a-purchase-decision.md`

비교를 종료하고 그 결과를 기록·관리하는 흐름을 소유한다.

- 구매 상품의 선택적 지정
- 목적과 후보의 일괄 아카이브
- 아카이브 스냅샷과 제목
- 아카이브 취소와 전체 복원
- 아카이브 기록 삭제

### `product/references/`

둘 이상의 사용자 흐름에서 반복해 사용하는 안정적인 정의만 둔다.

- `item-states.md`: 상태 용어, 공통 불변 조건, 상태 간 큰 전환
- `product-taxonomy.md`: 출시 기준 공용 taxonomy와 분류 체계 운영 원칙

각 상태를 만드는 행동과 예외 처리는 해당 기능 문서가 소유한다. reference 문서는 기능 흐름을 대신하지 않는다.

## 기능 문서 형식

```markdown
# 기능명

> 상태: 제안 | 확정 | 대체됨
> 최종 갱신:
> 관련 흐름:

## 사용자 목표
## 제품 원칙
## 범위
## 사용자 흐름
## 상태와 전환
## 예외와 복구
## 제품 규칙
## 미결정 사항
## 관련 문서
```

`사용자 목표`와 `제품 원칙`은 짧게 유지하되 생략하지 않는다. AI 에이전트가 세부 규칙을 다른 상황에 적용할 때 제품 의도와 상충하는 국소 최적화를 하지 않도록 판단 기준을 제공하기 때문이다. 긴 선택지와 trade-off는 history에 두고 링크한다.

## 제품 기획 history 구조

`history/product-planning/`의 버전은 문서 개정 횟수나 세션 수가 아니라 제품 출시 범위를 뜻한다.

- 현재 제품 기획 이력은 모두 `mvp/`에 둔다.
- 같은 출시 범위에서 기획이 바뀌어도 새 버전 폴더를 만들지 않는다.
- 이후 `v1/`, `v2/`는 해당 출시 범위의 구체적인 기획이 시작될 때만 만든다.
- 아직 구체화되지 않은 후보 기능 때문에 버전 폴더를 만들지 않는다.
- 날짜는 파일명에서 제거하고 문서 metadata와 Git 이력에 남긴다.

`mvp/checkpoints/`는 기존 체크포인트를 합치지 않고 의미별 이름으로 보존한다. `mvp/INDEX.md`가 시간 순서와 대체 관계를 설명한다. `mvp/decisions/`는 날짜·긴 prefix를 제거한 주제별 파일명을 사용한다.

기술 ADR은 제품 출시 범위와 독립적이므로 `history/architecture/`에 둔다. 기존 ADR 번호는 참조 안정성을 위해 유지하며 repository, client, server, ai 영역으로 분류한다.

## 변경 규칙

- 동일한 현재 규칙은 product 문서 하나만 소유한다.
- 다른 product 문서는 소유 문서의 해당 항목을 링크한다.
- 사용자 목표가 새로 구체화되면 기존 대형 문서에 계속 추가하지 않고 형제 product 문서가 필요한지 먼저 판단한다.
- 둘 이상의 흐름에서 같은 안정적 정의가 반복될 때만 reference로 승격한다.
- 미결정 사항은 구현자가 임의로 채우지 않도록 명시한다.
- 단순 문구 수정은 history 기록이나 새 제품 버전을 만들지 않는다.
- 제품 원칙, 인터페이스, 주요 사용자 흐름이 바뀌면 관련 history 결정과 product 문서를 함께 갱신한다.

## 마이그레이션 원칙

1. 현재 작업 트리의 내용을 기준으로 기존 product와 history 문서를 목록화한다.
2. 확정된 규칙마다 목표 product 소유 문서를 지정한다.
3. 새 product 문서를 먼저 작성하고 규칙 누락과 중복을 검토한다.
4. `product-spec.md`를 `product/overview.md`로 축소·이동하고 `product-taxonomy-draft.md`를 reference로 이동한다.
5. 기존 제품 기획 history를 `product-planning/mvp/` 아래로 이동한다. 본문은 보존하고 상태·대체 관계·현재 문서 링크만 필요한 만큼 갱신한다.
6. 기술 ADR을 `history/architecture/`로 이동하고 기존 번호를 유지한다.
7. 루트 및 하위 `INDEX.md`, `README.md`, 모든 내부 링크를 갱신한다.
8. 검증이 끝난 뒤에만 이전 경로의 파일을 제거한다. Git이 이동으로 인식할 수 있도록 내용 변경과 경로 변경을 구분해 검토한다.

## 검증

- 기존 `product-spec.md`의 확정 규칙이 하나 이상의 `product/*.md`에 배치됐는지 대조한다.
- 동일한 규칙이 여러 product 문서에서 독립적으로 정의되지 않았는지 확인한다.
- 모든 상대 Markdown 링크가 실제 파일을 가리키는지 검사한다.
- 이전 `product-spec.md`, `product-taxonomy-draft.md`, `history/PRODUCT-*` 경로 참조가 남지 않았는지 검색한다.
- taxonomy 상위 카테고리 11개와 세부 유형 87개가 누락 없이 이동했는지 확인한다.
- 기존 history 본문, 상태, 날짜, 결정 관계가 의도치 않게 손실되지 않았는지 diff로 검토한다.
- 사용자가 작업 전에 수정한 내용이 새 구조에 모두 반영됐는지 원본 diff와 비교한다.
- `docs/INDEX.md`에서 product, architecture, learning, history의 진입 경로가 모두 유효한지 확인한다.

## Trade-off

사용자 흐름별 문서는 화면별 또는 도메인별 문서보다 하나의 목표를 처음부터 끝까지 이해하기 쉽다. 반면 카테고리나 상태처럼 여러 흐름에 걸친 개념은 중복되기 쉽다. 이를 제한된 reference 문서와 단일 소유 규칙으로 보완한다.

출시 범위별 history는 같은 제품 단계의 논의를 한곳에서 볼 수 있지만, 한 결정이 여러 출시 범위에 걸쳐 유효할 수 있다. 현재 유효성은 product 문서에서만 판단하고, 이후 버전의 결정 문서가 이전 기록을 대체할 때 명시적 링크를 두어 해결한다.

## 재검토 조건

- product 문서가 많아져 `INDEX.md`만으로 사용자 흐름을 찾기 어려워질 때
- 하나의 product 문서가 서로 독립적인 사용자 목표를 둘 이상 소유하게 될 때
- reference 문서가 기능 동작까지 흡수해 새로운 대형 스펙이 될 때
- 출시 범위 명칭이 실제 배포 전략과 맞지 않게 될 때
- 자동 링크 검사만으로 문서 간 규칙 중복과 모순을 관리하기 어려워질 때
