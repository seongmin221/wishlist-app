# 제품 기획 재개 체크포인트 (2026-09-05)

> 상태: **진행 중** · 날짜: 2026-09-05 · 영역: **제품·서버·클라이언트·AI**

제품 정책 논의를 마친 지점과 다음 재개 위치를 기록한다. 제품 규칙의 기준 문서는 [제품 기능 및 스펙](../product-spec.md)이며, 아래 결정의 세부 근거는 연결된 결정 문서를 따른다.

## 이번까지 확정한 내용

### 목적과 카테고리

- 연결 상품이 있는 목적을 삭제하면 상품은 `확정된 목적 미지정`이 된다. 삭제 확인창에서는 대상 수와 펼쳐볼 수 있는 목록을 제공하며 실행 취소는 제공하지 않는다.
- 공용 카테고리는 사용자가 변경·삭제할 수 없다. 사용자 전용 카테고리만 변경·삭제할 수 있다.
- 사용자 전용 카테고리 이름 변경은 연결된 활성 상품에 즉시 반영한다.
- 사용자 전용 카테고리를 삭제한 뒤 상품별 재지정 흐름을 제공한다. 건너뛴 상품은 `정보 보완 필요`가 아니라 `카테고리 미지정` 영역에 둔다.
- 사용자 전용 카테고리는 사용자당 최대 20개다. 이름 40자, 설명 200자, 포함 예시 5개·각 60자로 제한한다.
- 형식 오류와 과도한 생성은 요청을 거부한다. prompt injection·URL·코드·유해 텍스트 중심 입력은 개인 목록에 유지하되 AI 후보에서만 제외하고, 이 내부 상태는 MVP 화면에 노출하지 않는다.
- 목적과 카테고리 이름은 아카이브 시점의 별도 스냅샷으로 보존한다.

### AI 목적 연결

- 상품 식별 정보와 기존 목적의 이름·설명·포함 상품에서 최소 근거를 찾을 수 있을 때만 자동 연결한다.
- 최소 근거를 충족하는 목적이 여러 개면 가장 부합하는 목적 하나를 연결하고 `분류·목적 확인`에서 검토하게 한다.
- AI가 연결한 미확정 항목만 관련 정보가 의미 있게 바뀌었을 때 다시 판단할 수 있다.
- 사용자가 확정한 목적은 목적 삭제 또는 직접 수정 전까지 자동으로 변경하지 않는다.
- 새 목적 생성 시 기존 상품 전체를 다시 판단하지 않고, 목적 삭제로 `확정된 목적 미지정`이 된 상품도 자동 재연결하지 않는다.
- 최초 추출 이후 상품 정보 변화를 주기적으로 모니터링하지 않는다.

### 중복 상품

- 활성 목록에 같은 canonical URL 또는 같은 상품으로 보이는 항목이 있어도 새 항목을 우선 생성한다.
- 추출 완료 후 `분류·목적 확인`에서 중복 후보를 비교하고, 새 항목 삭제·기존 항목 삭제·모두 유지 중 선택하게 한다.
- 기존 항목이 `PROCESSING`이면 판단을 미루고, `READY`는 중복 후보로 표시한다. `PARTIAL`은 확인 가능한 근거가 있을 때 후보로 표시하며, `FAILED`는 같은 URL의 기존 항목이 있다는 약한 안내만 제공한다.
- 아카이브에만 있거나 과거에 삭제된 동일 상품은 새로운 활성 항목으로 저장한다.

### 아카이브와 삭제

- 구매 결정 전 구매 상품과 함께 아카이브될 후보 수·목록을 확인한다.
- 아카이브 상세 화면에서만 아카이브 전체를 취소할 수 있다. 원래 목적과 모든 상품을 활성화하고 구매 결정을 취소한 뒤 아카이브 묶음을 제거한다.
- 개별 상품 복원·삭제는 제공하지 않는다. 아카이브 기록 삭제는 묶음 전체에만 허용하며 실행 취소는 제공하지 않는다.
- 활성 상품 삭제도 실행 취소를 제공하지 않는다. 확인창에는 연결 목적과 제거 사실을 표시하고, `?` 도움말에서 남은 상품 수·빈 목적 유지·기존 아카이브 비영향을 설명한다.

### 상품 링크 웹뷰

- 모든 상품 상태에서 앱 내 웹뷰로 원본 링크를 열 수 있다.
- iOS와 Android 모두 같은 탐색 규칙을 사용한다. 닫기는 좌측 상단, 뒤로·앞으로는 좌측 하단, 새로고침·공유는 우측 하단이며 공유 메뉴에 외부 브라우저 열기를 포함한다.
- 뒤로 가기는 웹페이지 기록을 우선하고 기록이 없으면 웹뷰를 닫는다. 새 창 요청은 현재 웹뷰에서 연다.
- 사용자가 누른 외부 앱 링크는 허용하고 자동 외부 앱 실행은 확인받는다.
- 쿠키는 방문 간 유지하고 설정에서 삭제할 수 있다. 외부 앱에서 복귀하면 웹뷰를 유지하며 강제 새로고침하지 않는다.
- 결제를 자동 감지해 구매 결정이나 아카이브를 수행하지 않는다.

### Product와 WishlistItem 경계

- `Product`는 canonical URL과 추출 metadata를 재사용하기 위한 공용 캐시다.
- `WishlistItem`은 표시용 상품 정보와 사용자 데이터를 자체 보관하는 생성 시점의 독립 snapshot이다.
- 새 항목 생성 시 `Product` 캐시를 한 번 복사할 수 있지만, 이후 두 데이터 사이에는 어느 방향으로도 동기화하지 않는다.
- `Product`가 보완돼도 기존 `WishlistItem`을 갱신하지 않고, 사용자 수정도 `Product`나 다른 사용자의 항목에 반영하지 않는다.
- 추출 작업은 새 저장 요청의 대상 상품만 처리하며 관련 상품이나 기존 항목을 연쇄적으로 갱신하지 않는다.

## 구현 상태

- 제품·서버·클라이언트·AI 정책과 구조 문서만 갱신했다.
- 앱과 서버 기능 구현은 아직 시작하지 않았다.
- 서버 MVP는 Kotlin/JVM + Ktor, 클라이언트 UI는 iOS SwiftUI와 Android Jetpack Compose, 공통 비즈니스 계층은 KMP를 사용한다.

## 다음 재개 지점

### 1. Product 캐시 상태별 재사용 기준 결정 (최우선)

아래는 논의 직전의 권장안이며 아직 확정하지 않았다.

- `READY`: metadata를 새 `WishlistItem`에 복사하고 상품 metadata 추출은 생략한다. 카테고리와 목적은 새 사용자 항목 기준으로 별도 판단한다.
- `PARTIAL`: 캐시를 재사용하지 않고 새 저장 대상만 다시 추출한다. 기존 항목은 갱신하지 않는다.
- `FAILED`: 캐시를 재사용하지 않고 새 저장 대상만 다시 추출한다. 이는 기존 항목 재시도가 아니라 새 요청의 추출이다.
- 캐시 유효기간: MVP에서는 만료 기간을 두지 않고 가격과 마지막 확인 시점을 함께 복사한다.

### 2. 이후 설계 순서

1. 확정된 제품 규칙을 반영한 전체 데이터 모델과 API 계약
2. PostgreSQL, Auth, Queue, Hosting 공급자와 처리 완료 전달 방식
3. JS-rendered 사이트에 대한 Playwright 적용 범위
