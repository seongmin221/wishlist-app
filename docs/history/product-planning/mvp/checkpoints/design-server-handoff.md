# 와이어프레임과 서버 작업 연결

> 상태: 전달 자료 검토 완료 · 2026-10-04 · 제품 규칙의 추가 확인과 서버 계약 정리 필요

## 사용자 요청

별도 워크스페이스에서 Claude Artifact로 디자인을 진행 중이며, 와이어프레임이 대략 나온 상태다. 이 디자인을 바탕으로 서버 작업을 이어가기 전에 디자인을 확인할 전달 방법을 조사한다.

## 확인 결과와 권장 전달 방식

이번 세션에서는 공유 링크의 웹 조회가 실패했고 직접 HTTP 요청은 403을 반환했다. 앱 내 브라우저 연결도 실패해 화면과 동작은 확인하지 못했다. 이 결과만으로 링크의 공개 여부나 사용자의 브라우저 접근 가능 여부를 판단하지 않는다.

권장 방식은 아티팩트의 소스 파일과 실행에 필요한 파일을 이 워크스페이스에서 읽을 수 있게 전달하고, 실행 화면을 함께 확인하는 것이다. 소스 공유가 어렵다면 주요 화면과 입력·완료·실패 상태의 스크린샷, 버튼별 동작 설명을 받는다. 전달 방식은 아직 사용자와 확정하지 않았다.

## 서버 작업으로 이어갈 기준

- 화면별 조회 데이터, 입력값, 사용자 동작과 상태 전이를 확인한다.
- 소스의 예시 데이터와 임시 동작을 서버 요구사항으로 자동 확정하지 않는다.
- [현재 제품 문서](../../../../product/INDEX.md)와 [서버 구조](../../../../architecture/server/overview.md), [기존 API 계약](../../../../architecture/wishlist-item-state-api.md)을 대조해 차이와 미결정 사항을 식별한다.
- 확인한 제품 규칙과 API 요구사항을 해당 현재 문서에 반영한 뒤 서버 구현 범위를 정한다.

최초 조사 시점에는 디자인 검토나 디자인에 근거한 서버 변경을 수행하지 않았다.

## 브랜치 자료 검토

사용자가 `design/handoff` 브랜치로 전달했다. 검토 기준은 `c59741dec07704844c95eec026870ff7d89db5b4`이며, 로컬과 origin 브랜치가 같은 커밋임을 확인했다. 별도 디자인 워크트리의 변경 사항이 없는 상태에서 자료를 읽었고, 서버 브랜치에는 병합하지 않았다.

자료는 `design/handoff/wireframes/`의 README, manifest, 보드 HTML 43개와 FlowMap, 해당 PNG 44개, 런타임과 캡처 스크립트다. README는 HTML을 화면 구조 기준, PNG를 첫 화면 참고로 정하고, 디자인 결정과 제품 문서의 우선순위도 설명한다. 주요 보드의 상태 처리 코드와 FlowMap·홈·후보 추가 PNG를 확인했으며 디자인 브랜치의 제품 문서와 서버 브랜치의 API 계약을 대조했다. 브라우저에서의 실제 클릭 검증은 수행하지 않았다.

화면 구조와 정상 흐름을 파악하고 서버 작업 범위를 정리하기에는 충분하다. 전체 시각 디자인이나 아티팩트의 원본 대화가 서버 작업 시작의 필수 자료는 아니다.

### 전달 사본과 문서의 불일치

- `PurposeCreate.dc.html`, `PurposeHome.dc.html`은 `아이콘 · 선택`을 표시하지만 제품 문서와 최신 디자인 결정은 필수다. 최신 규칙을 기준으로 사본의 문구와 필수 검증을 맞춰야 한다.
- Home PNG에는 미리보기 캐러셀이 처음부터 보이지만 2026-10-03 디자인 결정은 펼쳤을 때만 표시하도록 바뀌었다. 서버의 새 요구사항이 아니라 사본 갱신 문제다.
- `HomeReviewFlow`의 카테고리·목적 변경 버튼, `HomeFillFlow`의 다시 분석·카테고리 선택 등 일부 버튼에는 실행 핸들러가 없다. 소스만으로 모든 실제 동작을 확인할 수 없으며 README에 미구현 인터랙션을 명시하면 해석에 도움이 된다.
- manifest에는 원본 URL과 화면 정보가 있지만 추출 일시·원본 버전은 없다. 다음 갱신부터 추출 일시와 어떤 디자인 결정까지 반영했는지를 기록하면 시점 차이를 줄일 수 있다.

### 서버에서 정리할 기술 과제

이 항목들은 디자인 담당자에게 API 설계를 요청할 사안이 아니다. 위 제품 확인 결과를 바탕으로 서버 작업에서 구체화한다.

- 기존 `requiredAction`은 카테고리 지정·재지정을 분리하지만 새 화면은 정보 보완으로 묶는다. 내부 누락 원인은 보존하면서 홈 조회·건수·연속 처리의 투영을 일치시킨다. `READY` 항목의 카테고리 삭제 후 재지정은 기존 manual-completion의 허용 상태와도 조정해야 한다.
- 상품 편집·직접 보완 계약에 브랜드, 목적 색·아이콘의 안정된 식별자와 기본값, 화면 표시용 판매처·metadata 확인 시점을 검토한다. 흑백 색상값이나 배열 인덱스를 그대로 영속 모델로 사용하지 않는다.
- 홈 요약, 카테고리별 건수, 목적 CRUD·후보 일괄 이동, 아카이브 생성·조회·제목 수정·복원·삭제 API를 구체화한다. 후보 일괄 이동과 아카이브의 동시 변경 처리도 정한다.
- 사진 보관함 이미지의 업로드·저장·접근 권한·수명주기는 기술 설계가 필요하다. 이미지 선택의 제품 요구는 이미 있으며 공급자와 구현 방식은 서버에서 정리한다.
- 기존 제품 문서의 미결정 목록 중 와이어프레임에서 이미 구체화한 편집·확인창 내용은 최신 상태로 정리한다.

서버 구현은 이번 검토에서 변경하지 않았다. 다음 단계는 제품 확인이 필요한 항목의 답을 반영하고, 디자인 브랜치의 제품 변경을 서버 계약과 연결하는 것이다.
