# C3 PR #12 리뷰 반영 (2026-10-09)

> 브랜치 `client/c3-share-save`(draft PR #12) · 시작 `f4972f3` · 현재 구조는 [KMP](../../../architecture/client/kmp.md)·[Android](../../../architecture/client/android.md)·[iOS](../../../architecture/client/ios.md) 문서가 기준이다

PR 리뷰에서 나온 10건을 코드로 확인한 뒤 고쳤다. 동작 결함 4건, 효율·정리 6건이다. 공개 API 변경은 `HomePresenter.refreshNow()` 추가와 `DisplayFormat.relative`의 offset 인자 형식뿐이다.

## 지적과 수정

| # | 지적 | 수정 | 테스트 |
| --- | --- | --- | --- |
| 1 | 로그아웃 상태(또는 데이터가 같은) refresh는 같은 `SubmissionView`를 다시 게시해 StateFlow가 버린다. 상대 시각은 사용자 당김에서만 다시 계산됐다 | coordinator가 internal `refreshes: StateFlow<Long>`(끝난 refresh 실행 수, 모든 트리거·로그아웃 포함)을 내보내고 HomePresenter가 이를 결합한다. HomePresenter에 foreground intent는 추가하지 않았다(판정 A) | `RuntimeSubmissionsTest` 로그아웃·로그인 각각: 저장 직후 JustNow → 3시간 뒤 `refresh(FOREGROUND)`(데이터 변화 없음) → `Hours(3)`. `HomePresenterTest` revision만 바뀌어도 다시 계산 |
| 2 | 복원은 저장 계정을 ready 전에 게시한다. AccountPresenter가 그때 `markFirstRunLoginSeen()`을 불러 gated facade가 버리고, 플래그가 저장되지 않는다 | 계정 관찰을 `restored` 뒤로 옮겼다. 복원 전에 본 계정도 ready 뒤 현재 값으로 다시 보고 저장한다 | `SharedModulesTest`(inline dispatcher로 ready 전 관찰을 재현): 저장 로그인 복원 → `onboarding.login.seen = "1"`, 로그아웃 뒤 새 Presenter의 `showFirstRunLogin == false`. `AccountPresenterTest`도 같은 순서를 facade 대역으로 확인 |
| 3 | `importInbox`가 ready를 1500ms만 기다려 느린 DEBUG cold start에서 inbox 전체가 retained가 되고 다음 refresh는 다시 가져오지 않는다 | `importInbox`는 시간 제한 없이 기다리고, coordinator scope가 닫히면 retained로 돌아온다. 대기는 scope 안의 `async`라 runtime close가 끝낸다. `receiveShared`는 1500ms 그대로(판정 B) | ready가 5000ms(virtual) 뒤 → 가져와 deletable. ready 전 close → retained로 반환 |
| 4 | 상대 시각이 두 시각 모두 `now`의 offset으로 날짜를 계산해 서머타임 경계에서 틀린다 | `relative(from, now, utcOffsetSeconds: (Instant) -> Int)`로 바꿔 각 시각의 offset을 쓴다. 플랫폼 `PlatformResources.utcOffsetSeconds`는 이미 시각별 함수였다 | offset이 UTC+0 → +1로 바뀌는 경계: 23:30(+0) 저장, 다음 날 01:45(+1) → `Yesterday`(이전 계산은 `Hours(1)`) |
| 5 | `send()`가 행마다 view 계산 전체를 launch해 flush 비용이 O(N²) | conflated channel + publisher coroutine 하나로 게시를 합친다. 중간 갱신은 요청만, flush 끝·refresh 끝·수신·import는 직접 게시해 `refresh` 반환 때 최종 상태를 보장한다 | 100행 flush(즉시 응답 fake ITEM-01): `pending()`·`processingItems()` 각 3회(단언 상한 4, 이전 102회 이상), 최종 view 순서 확인 |
| 6 | Android cold start에서 Application의 LAUNCH와 MainActivity 시작의 FOREGROUND로 refresh가 두 번 돈다 | Application LAUNCH를 없애고, 첫 0 → 1 전이가 LAUNCH·이후가 FOREGROUND다(iOS와 같음, 판정 D). 전이 판단을 순수 클래스 `ForegroundTransitions`로 나눴다 | `ForegroundTransitionsTest`(첫 시작 LAUNCH 한 번, 배경→앞 FOREGROUND, 구성 변경 무시, 공유 Activity 무시) |
| 7 | iOS 당겨서 새로고침이 30ms polling·300ms 추정·30초 상한으로 끝을 짐작한다 | `HomePresenter.refreshNow()`(같은 의미, 끝날 때 반환, 실행 중·close 뒤 즉시 반환)를 추가하고 iOS owner가 SKIE async로 기다린다. `CancellationError`는 조용히 버린다 | `HomePresenterTest.refreshNowReturnsOnceTheRefreshFinished`. XCTest `HomePresenterOwnerTests`: ITEM-01 800ms 지연 전송이 끝난 뒤에 반환 |
| 8 | 정렬이 SQL·`publishView`·HomePresenter 세 곳에 있다(`selectProcessingItems`의 ISO text 정렬은 소수 초에서 틀림) | 정렬 지점은 coordinator view 하나다(판정 C). `local`은 SQL `(shared_at_us, key)` 순서(`prepareFlush`가 기댐), `processing`은 `publishView`에서 `(createdAt, id)`. `selectProcessingItems`의 `ORDER BY`와 HomePresenter의 두 정렬을 지우고 `SubmissionView`·`LocalStore.processingItems` KDoc에 적었다 | 정확한 순서 테스트(정렬 안 된 입력, 같은 createdAt의 id 순, 소수 초)를 `SubmissionCoordinatorTest`로 옮겼다. `HomePresenterTest`는 view 순서 유지(local 다음 processing)만 확인한다 |
| 9 | 링크 정규식이 따옴표와 `>`를 이미 빼므로 `ShareTextParser`의 따옴표 분기와 `>` 짝은 실행될 수 없다 | 둘을 지워 Swift extractor와 같은 표로 맞췄다 | 공유 벡터 테스트를 바꾸지 않고 통과 |
| 10 | `DebugControls.createUnboundPending`(`wl.fake.pendingCount`)이 호출자 스레드(main)에서 SQL을 실행한다 | 저장을 runtime io dispatcher의 `withContext`로 옮겼다 | io 기록 dispatcher로 각 저장의 key 조회가 io에서 돈 것을 확인 |

RED는 각 테스트를 먼저 넣고 확인했다. 1·2·3·5·8·10은 단언 실패(예: 1은 `expected Hours(3) but was JustNow`, 5는 `pending() calls: 102`, 10은 `[false, false]`), 4·6·7은 새 시그니처·클래스·함수가 없어 컴파일 실패, 9는 동작 변경이 없는 삭제라 기존 테스트 GREEN 유지다. iOS owner 테스트는 이전 polling 구현에서도 통과하는 회귀 테스트다.

## 남은 점

- 판정 1의 revision은 Kotlin internal이라 다른 화면이 쓰려면 같은 방식으로 runtime에서 연결해야 한다.
- 2의 runtime 수준 재현은 inline dispatcher에 기댄다(테스트 dispatcher에서는 bootstrap이 한 번에 돌아 경합이 생기지 않는다).
- 6 이후 공유 카드만 띄운 프로세스는 LAUNCH refresh를 보내지 않는다(공유 수신 자체가 로그인·온라인이면 전송을 요청한다).
