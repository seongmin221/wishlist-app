# C5 카테고리 설계 검토 (2026-10-14)

검토 대상: [C5 설계 초안](../../../superpowers/specs/2026-10-14-client-c5-category-design.md).
서버 CAT-01~04·ITEM-02 계약과 현재 C4 이미지·입력·내비게이션 구현을 대조했다.
아래는 수정 제안이며 제품 결정 D1~D14를 새로 확정하거나 원문에 반영한 기록은 아니다.
코드를 변경하거나 앱 테스트를 실행하지 않았다.

전체 방향(화면별 shared Presenter, API 단위 repository, C8/C9/C7 경계, PR A/B 분리)은 타당하다.
구현 계획으로 옮기기 전에 다음 계약을 보완하는 것을 권한다.
P1은 핵심 동작을 구현하려면 먼저 해결할 항목, P2는 예외 경로·표시 규칙을 명확히 할 항목이다.

## 1. P1 — 추가 폼에 전체 상위와 사용 개수를 공급하는 경로가 없다

대상: 설계 §2 `CategoryHomePresenter`·`CategoryFormPresenter`, §3 추가 시트(60~66, 81행).

첫 화면은 BROWSE만 조회하지만 추가 시트는 상위 11개를 모두 표시해야 한다.
[CAT-01 계약](../../../architecture/server/category-management-api.md#cat-01-공개-조회)에서
BROWSE는 노출 leaf가 있는 상위만 반환하며 빈 계정에서는 groups가 비어 있다.
따라서 첫 화면 데이터를 재사용하면 빈 탭에서 상위를 고를 수 없고,
일부 상품만 있는 계정에서도 나머지 상위 아래에 만들 수 없다.
`startCreate(parentId?, source)`에는 usage 인자도 없고 폼의 catalog 조회도 정의되지 않았다.

제안: 폼이 생성 시작 때 CAT-01 SELECT를 조회해 전체 상위·usage를 받거나,
호출자가 SELECT 결과를 전달하도록 계약을 명시한다.
폼 state에 초기 로딩·초기 조회 실패·재시도를 추가하고 준비 전 제출을 막는다.
빈 계정, BROWSE에 상위 하나만 있는 계정, SELECT 실패를 테스트한다.

## 2. P1 — 사진 캐시 재사용 조건이 현재 iOS 로더와 맞지 않는다

대상: 설계 §3 사진 배치, §4 공유 요소 전환(85, 99행).

[RemoteImageLoader](../../../../client/ios/Wishlist/Platform/RemoteImage.swift)는 메모리 캐시와
진행 중 요청을 `(URL, 칸 픽셀 크기, fill/fit)`로 구분한다.
카드와 상세의 칸 크기는 달라 URL이 같아도 캐시 키가 다르다.
`pixelSize` 역시 private이며 현재 크기 조회를 독립적으로 공유하는 API가 없다.
URLCache가 재다운로드를 줄일 수는 있지만, 같은 메모리 이미지나 진행 중 요청의 공유를 보장하지 않는다.
현재 계약만으로는 "같은 이미지 cache key"와 "전환 중 다시 받지 않음"을 충족할 수 없다.

제안: URL 단위 원본 데이터·크기·진행 중 요청 공유와 표시 크기별 다운샘플 캐시를 구분한다.
전환은 이미 표시 중인 카드 이미지를 유지하고 상세 크기 이미지는 별도로 준비하는 방식을 명시한다.
로더 변경을 PR A(크기 수집)와 PR B(전환 재사용)의 작업 범위에 포함한다.
콜드 캐시·동시 크기 조회/카드/상세 요청·메모리 캐시 축출·EXIF 회전 이미지를 검증한다.
로더 호출 횟수와 실제 네트워크 다운로드 횟수는 구분해서 확인한다.

## 3. P2 — 조회용 취소 규칙을 생성·편집 제출에 그대로 적용하기 어렵다

대상: 설계 접근 방식 1, §2 폼의 제출·멱등 key·닫기(31, 66~69행).

설계는 C4의 "마지막 요청 승리"를 따르지만 제출 중 중복 저장, 입력 변경,
뒤로·시트 닫기를 허용하는지 정하지 않았다. 요청 취소는 서버 commit을 취소한다는 뜻이 아니다.
예를 들어 생성이 서버에서는 성공하고 응답만 유실된 뒤 parent를 바꾸어 새 key로 제출하면,
두 상위에 각각 카테고리가 생길 수 있다. 동일 payload 재시도 key 규칙만으로 이 경로는 해결되지 않는다.

제안: 제출은 한 번에 하나만 허용하고 key와 전송 payload snapshot을 함께 보관한다.
제출 중 입력·닫기 동작, 성공 여부가 불명확한 실패 뒤 payload 변경/재제출 정책을 명시한다.
계정 이탈 때는 기존 계약대로 닫되 늦은 응답을 새 계정에 반영하지 않는다.
"commit 뒤 응답 유실 → 같은 payload 재시도", 빠른 두 번 제출,
제출 중 닫기·계정 변경을 테스트한다.
한도 선검사는 새 생성에 적용하되 이미 전송한 동일 payload replay까지 막지 않도록 구분한다.
[서버 계약](../../../architecture/server/category-management-api.md#cat-03-생성과-replay)은 replay를 한도 검사보다 먼저 처리한다.

## 4. P2 — 편집 초기 조회와 409 복구 재조회가 실패했을 때의 상태가 없다

대상: 설계 §2 `startEdit`와 409 처리(64, 68행).

초기 CAT-02 실패 때 빈 폼을 보여 줄지, 오류 화면을 보여 줄지 정의되지 않았다.
또한 PATCH가 409를 반환한 뒤 최신 CAT-02가 연결 실패하면 새 version을 얻지 못한 상태다.
그 상태에서 저장을 다시 허용하면 오래된 expectedVersion으로 409를 반복할 수 있다.
최신 조회가 404가 되면 폼 교체도 불가능하다.

제안: 초기 로딩/오류와 충돌 복구 로딩/오류를 구분하고 최신 baseline을 받기 전에는 저장을 막는다.
복구 실패는 CAT-02 재조회로 재시도하고, 404는 Gone으로 끝낸다.
D11의 입력 폐기는 최신 상세를 성공적으로 받은 때 적용하며,
"불러왔어요" notice도 그 시점에만 표시한다.
초기 404·연결 실패, 409→조회 실패→재시도 성공, 409→404를 테스트한다.

## 5. P2 — code point 길이 제한을 기존 입력 컴포넌트에 연결하는 방법이 필요하다

대상: 설계 §1 입력 규칙, §6 입력 검증(50, 131~134행).

[Android WLInput](../../../../client/android/src/main/kotlin/app/wishlist/android/designsystem/WLInput.kt)은
grapheme 단위 제한을 쓰며 composition 중에는 자르지 않는다.
[iOS WLInput](../../../../client/ios/Wishlist/DesignSystem/WLInput.swift)도 String.prefix 기반 제한과
marked text 보호를 사용한다. 새 순수 함수만 추가하거나 기존 maxLength에 40을 넣는 것으로는
서버의 code point 계약을 적용할 수 없다. 반대로 매 입력마다 Presenter에서 문자열을 자르면
기존 한글 IME 조합 보호를 우회할 수 있다.

제안: 길이 측정·절삭 정책을 주입하거나 C5용 입력 어댑터를 두되 조합 중 입력을 보존한다.
조합 확정 뒤 code point 제한을 적용하고 저장 직전에도 검증한다.
surrogate 쌍을 절단하지 않는 규칙을 명시한다.
한계 직전 한글 조합, NFD 한글, ZWJ 이모지 붙여넣기,
조합 중 예시 완료/저장 동작을 두 플랫폼에서 검증한다.

## 6. P2 — 카드 확인 시각이 null인 정상 응답의 표시 규칙이 빠져 있다

대상: 설계 D8, §3 목록 카드, §5 문구(20, 83, 103행).

[ITEM-02 계약](../../../architecture/server/wishlist-item-read-api.md#공용-카드와-pagewindow)에서
metadataCheckedAt은 nullable이며 이름이 있는 PROCESSING 상품도 카테고리 목록 대상이다.
따라서 모든 카드에 "N일 전 확인"을 붙일 수 없다.
생성/분류 시각으로 대체하면 metadata 확인 시각을 대신 쓰지 말라는 서버 계약과 충돌한다.

제안: null이면 확인 시각 부분과 앞 구분점만 숨기고 목적 부분은 유지한다.
시각이 있으면 기존 상대 시각 함수를 재사용할지, D8대로 일 단위만 쓸지 정한다.
보드의 "1주 전 확인"과 D8의 "N일 전 확인" 표현도 통일한다.
null·오늘·어제·일/주 경계와 ko/en을 테스트한다.

## 추가 권고

- **같은 version 캐시의 최신성 표현:** §1의 `version >=`는 기존 GET 규칙과 일치한다.
  다만 category 편집은 item version을 올리지 않으므로 늦게 도착한 같은 version 목록 응답이
  최신 표시명을 덮을 수 있다. "최신이 된다"는 보장을 완화하거나, 편집 전 진행 중 조회를
  무효화하는 규칙을 추가한다. C7까지 남길 한계라면 명시한다.
- **부분 조회 실패:** 목록의 CAT-01·CAT-02·ITEM-02 중 일부만 실패할 때,
  카드 로딩을 계속할지, hint와 totalCount 중 어느 값으로 머리를 그릴지 정한다.
  header-only refresh 메서드도 Presenter 계약에 추가하면 플랫폼이 전체 목록 refresh를
  호출해 위치를 잃는 실수를 줄일 수 있다.
- **검증 데이터:** 기본 seed는 전체 69개이고 헤드폰은 8개여서 특정 카테고리의
  40개 페이지 경계를 검증할 수 없다. 별도 DEBUG fixture로 같은 카테고리 120개를 준비한다.
  MockEngine 공통 테스트는 클라이언트의 wire 처리 확인이며 서버 구현 검증과는 구분한다.
- **문서 연결:** specs INDEX에 C5를 등록하고, 문서 갱신 대상의 디자인 결정 범위를
  D5~D13에서 D14까지 포함하도록 정리한다.

## 2차 검토 — 1회 반영 초안

SELECT 공급, 편집 초기 조회·409 재조회 실패, 제출 중 중복 요청·닫기 차단,
code point 입력 어댑터와 IME 보호, 확인 시각 null 표시는 반영됐다.
응답 유실 뒤 다른 payload로 생성하면 생길 수 있는 추가 생성도 한계로 명시됐다.
사진은 크기 조회와 실제 로딩을 한 번으로 합치고 상세의 초기 이미지 재사용 방향을 정했다.
아래 네 항목은 구현 계획에 추가할 보완 사항이다. 모두 P2로 분류한다.
행 번호는 1회 반영 초안 기준이다.

### R2-1. 사진 표시 비율과 디코드 메모리 상한을 분리한다

대상: 설계 95행, 사진 배치.

새 방식은 40개 사진을 열 폭 기준·높이 무제한으로 받아 배치 전부터 디코드한다.
비율이 매우 긴 상품 이미지는 작은 열 폭에서도 큰 비트맵이 된다.
예를 들어 폭 480px·세로/가로 비율 100인 이미지를 그대로 디코드하면
4바이트 픽셀 기준 약 88MiB다(480 × 48,000 × 4).
현재 iOS 로더의 캐시 비용도 픽셀 수 × 4로 계산하며,
캐시 한도는 디코드 순간이나 페이지 상태가 보유한 이미지의 총량을 제한하는 계약이 아니다.
3초 skeleton 제한 역시 이미지 작업의 메모리 상한을 정하지 않는다.

제안: D10의 표시 비율은 유지하되 비트맵 최대 픽셀 수/긴 변,
동시 요청 수와 화면 밖 이미지 보유 범위를 별도로 정한다.
레이아웃 비율은 EXIF 회전을 적용한 원본 크기에서 계산하고,
디코드 결과가 축소돼도 그 비율을 유지한다.
Android도 디코더 제한에 따른 결과 크기를 원본 비율로 간주해도 되는지 확인한다.
일반 비율 120개뿐 아니라 긴 이미지 여러 개와 느린 요청이 섞인 페이지를 검증한다.

### R2-2. 캐시 키만으로 전환 사진을 보장하지 않는다

대상: 설계 113~115행, 사진 캐시 계약.

`bestCached`와 `placeholderMemoryCacheKey`는 해당 이미지가 메모리 캐시에 있어야 동작한다.
카드가 자체 상태로 이미지를 표시하고 있어도 캐시에서는 축출된 상황을 별도로 다뤄야 한다.
[Coil 공식 가이드](https://coil-kt.github.io/coil/recipes/#shared-element-transitions)도
사진이 메모리 캐시에 있을 때 깜빡임을 피하는 방식으로 설명한다.
iOS의 URLCache 역시 메모리 이미지의 대체 수단이 아니며,
"주소가 하나라 다시 받지 않는다"는 문장은 디스크 캐시 miss를 고려하지 않는다.
[Apple URLCache 설명](https://developer.apple.com/documentation/foundation/urlcache)은
요청별 응답 캐시이며 디스크 용량도 유한하다고 설명한다.

제안: 전환 시작 때 현재 표시 중인 카드 이미지 참조를 전환 상태가 보유하고,
전환 완료·취소 때 해제한다. URL별 검색은 보조 경로로 둔다.
현재 표시 사진을 확보하지 못하면 placeholder 또는 slide로 가는 fallback을 정한다.
고해상도 이미지 준비와 전환 이미지 유지는 분리하고 재다운로드 가능성은 허용/조건부로 기술한다.
카드는 보이지만 메모리 캐시를 비운 상태에서 push·pop·끌어서 뒤로 취소를 검증한다.

### R2-3. 목록 머리 갱신과 부분 실패의 Presenter 계약이 여전히 없다

대상: 설계 66, 97, 101행.

편집 뒤에는 목록 머리만 갱신한다고 했지만 공개 동작에는 전체 페이지를 버리는
`refresh()`만 있다. 플랫폼이 이를 호출하면 D3의 목록 위치 유지와 충돌할 수 있다.
또한 CAT-01/CAT-02 실패를 ITEM-02 성공과 어떻게 조합하는지도 아직 정의되지 않았다.

제안: `refreshHeader()` 또는 `onCategorySaved(detail)`를 명시하고
items·nextCursor·이미 확정한 카드 높이를 보존한다.
머리 조회 실패 시 기존 머리/hint와 카드는 유지하고 안내를 표시한다.
count의 출처/적용 우선순위, CAT-02/ITEM-02의 custom 404가 Gone이 되는 조건을 정한다.
3페이지를 붙인 상태에서 이름 편집 후에도 항목·cursor·스크롤이 유지되는지,
CAT-01만 실패해도 성공한 상품 목록이 보이는지 테스트한다.
이 항목은 1차 추가 권고에서 미해결로 남았다.

### R2-4. 서버의 fields를 ClientError에 보존하는 변경을 포함한다

대상: 설계 §1 Remote(44행), §2 폼 오류(75행), 작업 묶음 1.

현재 [ClientError](../../../../client/shared/src/commonMain/kotlin/app/wishlist/shared/core/ClientError.kt)에는
`fields`가 없고 [ApiErrorMapper](../../../../client/shared/src/commonMain/kotlin/app/wishlist/shared/data/remote/ApiErrorMapper.kt)는
details에서 currentVersion만 읽는다. 따라서 기존 mapper를 그대로 재사용하면
`INVALID_CATEGORY_INPUT`의 이름/설명/예시 오류 위치를 Presenter가 알 수 없다.
Fake가 자체 검증으로 오류 칸을 아는 것과 Remote가 서버 오류를 전달하는 것은 별도 경로다.

제안: ClientError에 허용된 필드 목록을 추가하거나 카테고리 전용 오류 타입을 둔다.
알 수 없는 필드명은 무시하고 필드 정보가 없으면 폼 공통 오류로 처리한다.
원문 사용자 입력을 오류에 포함하지 않는 서버 경계는 유지한다.
MockEngine으로 description/examples 필드 오류가 해당 칸까지 전달되는지 확인한다.

### 작은 문서 정리

- 생성 SELECT snapshot을 넘기는 인자를 `startCreate` 시그니처에도 표시한다.
- `canSubmit`의 최종 조건에 Ready·제출 중 아님·입력 검증 성공을 함께 적고,
  이미 보낸 생성 payload replay는 신규 생성 한도 선검사와 구분한다.
- 409 복구에서 "이미 반영됨"은 category 전체 객체가 아니라 마지막 전송 payload를
  적용한 name/description/examples의 기대 결과와 비교한다고 적는다.
  다른 기기가 같은 값을 저장했을 수도 있으므로 "내 저장 성공 확인"보다는
  "원하는 값이 이미 반영됨"이 정확하다.
- 같은 version 캐시 응답의 역전 한계, 120개 전용 fixture, D14 문서 갱신 대상은
  1차 추가 권고 그대로 남아 있다.

## 3차 검토 — 2회 반영 초안

R2-1~4의 설계 보완을 확인했다. 원본 비율과 디코드 픽셀 상한 분리,
동시 요청 제한, PhotoHandoff, refreshHeader/applyEdited와 부분 실패,
ClientError.fields 전달이 추가됐다. 같은 version 캐시 역전은 알려진 한계로 남겼고
120개 fixture도 명시했다. 아래 두 항목은 새 계약을 기존 iOS 구현에 연결할 때
필요한 변경 범위다. 모두 P2이며 설계 전반을 다시 바꿀 항목은 아니다.

### R3-1. iOS 로더 내부 작업까지 취소를 전달한다

대상: 설계 100행의 화면 밖 요청 취소·동시 요청 6개, 작업 묶음 4.

[RemoteImageLoader.load](../../../../client/ios/Wishlist/Platform/RemoteImage.swift:93)는
다운로드·디코드를 별도 `Task`로 만들고 호출자는 `task.value`를 기다린다.
호출자 취소를 내부 task에 전달하거나 마지막 대기자가 떠났을 때 내부 task를
취소하는 처리가 현재 없다.
[Swift 공식 문서](https://docs.swift.org/swift-book/LanguageGuide/Concurrency.html)는
이런 비구조적 task에는 부모 task가 없다고 설명한다.
화면의 semaphore와 `.task` 취소만 추가해서는 "화면 밖 요청 취소"를 충족하지 못한다.
기존 load가 끝날 때까지 슬롯을 유지하면 불필요한 작업이 슬롯을 차지하고,
호출자 취소 즉시 슬롯을 반환하도록 구현하면 내부 작업이 계속되는 동안
새 요청이 시작돼 실제 진행 작업이 제한을 넘을 수 있다.

제안: 로더 내부 작업의 취소·슬롯 수명을 작업 범위에 넣는다.
같은 key를 여러 화면이 기다릴 수 있으므로 대기자 하나가 취소됐다고
공유 작업 전체를 무조건 취소하지 말고, 마지막 대기자가 떠난 때 취소하도록 정한다.
실제 다운로드/디코드 작업이 끝나거나 취소를 처리한 뒤 슬롯을 반환한다.
느린 URL 6개 요청 중 스크롤 이탈→새 URL 요청, 같은 key 대기자 둘 중 하나 취소,
전체 대기자 취소를 테스트하며 wrapper 호출 수와 실제 진행 작업 수를 구분한다.

### R3-2. 뒤로 전환의 사진 공급원을 내비게이션 전환층에도 연결한다

대상: 설계 120~121행의 "뒤로 갈 때 상세가 그리고 있는 이미지"와 변경 범위.

현재 [WLNavHost](../../../../client/ios/Wishlist/Navigation/WLNavHost.swift:152)는
push/pop 모두 `registry.photo(entry.sourceKey)`를 전환층에 넘긴다.
[WLSharedPhotoTarget](../../../../client/ios/Wishlist/Navigation/WLSharedElement.swift:161)은
상세의 사각형만 등록하며 사진 builder는 등록하지 않는다.
따라서 상세 사진 자리에 PhotoHandoff를 연결하는 것만으로는
뒤로 전환층이 상세의 현재 사진을 쓰게 되지 않는다.
상세가 고해상도 사진으로 바뀐 뒤 pop하면 목록 사진으로 돌아가거나,
목록 source가 해제됐으면 사진 공급원을 잃을 수 있다.

제안: PR B 범위에 `WLSharedPhotoTarget`의 사진 공급원 등록과
`WLNavHost/WLNavMotion`의 방향별 전환 이미지 선택을 포함한다.
push 시작에는 카드, pop/끌어서 뒤로 시작에는 상세의 현재 이미지를 확보하고
각 모션 동안 그 참조를 유지한다. 끌어서 뒤로 취소 뒤에도 상세 사진을 유지한다.
설계 끝의 "상세 쪽 변경은 공유 key와 진입 방식 인자뿐" 문장은 이 범위에 맞춰 수정한다.
카드 저해상도→상세 고해상도 교체 뒤 pop, 상세에서 이미지 변경 뒤 pop,
목록 source가 없는 상태와 뒤로 끌기 취소를 검증한다.

### 남은 제품 결정

D15(확인 시각의 분/시간/일 또는 주 단위 표현)는 문서에 결정 대기로 표시돼 있다.
기술 결함은 아니며 카드 문구·경계값 테스트를 확정하기 전에 선택하면 된다.
이번 검토에서 별도로 확정하지 않았다.

## 4차 검토 — 3회 반영 초안

R3-1의 iOS 공유 요청 대기자 수·마지막 대기자 취소·로더 내부 실제 작업 기준
동시 제한과 검증 사례가 PR A 범위에 추가됐다.
R3-2의 target 사진 등록·방향별 전환 이미지 선택·뒤로 끌기 취소 시 유지가
PR B 범위에 추가됐고 Android 역방향 handoff도 명시됐다.
이전 지적은 설계 수준에서 반영됐으며, 이번 검토에서 추가 P1/P2 문제는 발견하지 못했다.
구현 계획 작성으로 진행할 수 있다. 구현 정확성과 성능 통과를 확인한 것은 아니다.

남은 사항은 다음과 같다.

- **제품 결정:** D15 확인 시각 표현은 여전히 대기다. 관련 문구·경계값 테스트를
  확정하기 전에 결정한다. 다른 데이터·Presenter 작업을 막지는 않는다.
- **작은 문구 정리:** §4 끝의 "상세 쪽 변경은 사진 자리의 공유 key와 진입 방식
  인자뿐"은 앞서 추가한 현재 이미지 등록·handoff 공급 범위보다 좁다.
  해당 요약만 새 범위에 맞춰 정리하면 된다. 작업 묶음 5에는 변경 범위가 이미 들어 있다.

검토 기록과 INDEX만 갱신했다. 설계 원문·코드는 변경하지 않았고 앱 테스트는 실행하지 않았다.
