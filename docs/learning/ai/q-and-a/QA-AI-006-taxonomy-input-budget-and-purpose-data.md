# AI 분류 후보를 모두 보낼 수 없는 이유는 무엇인가

## 질문

공용 상품 유형 87개가 있는데 왜 AI Worker를 바로 켤 수 없으며, 입력 상한과 사용자 목적 데이터는 어떤 관계인가?

## 답변

AI가 상품을 분류하려면 상품 설명과 함께 **선택 가능한 유형의 ID와 이름**을 받아야 한다. `C026`이라는 ID만 보내면 모델은 이것이 `헤드폰`인지 알기 어렵다. 프로젝트에는 확정된 공용 유형 87개가 있고, 현재 이 ID·그룹·이름을 버전 데이터로 보관한다.

문제는 비용 보호를 위해 합의한 **호출당 입력 최대 1,000 token**과 현재 코드의 **요청 전체 최대 900 UTF-8바이트**가 서로 다른 단위라는 점이다. 900바이트는 실제 token 수를 세는 기능이 아니라 과다 입력을 막기 위한 매우 보수적인 임시 guard다. 87개 ID·그룹·이름만 간단히 이어도 약 3,845바이트라 이 guard에는 들어가지 않는다. 그렇다고 3,845바이트가 곧 3,845 token이라는 뜻은 아니다. 정확한 token 수는 모델과 요청 구조·출력 schema에 따라 달라지며, OpenAI는 실제 Responses 요청과 같은 형식으로 입력 token을 세는 API를 제공한다.

따라서 전체 후보를 그대로 보내려면 실제 요청의 token 수를 측정하고, 1,000 token 안에 들어가는지 확인해야 한다. 초과한다면 (1) 상품 정보로 후보를 먼저 좁히고 분류 정확도를 평가하거나, (2) 입력 상한과 호출 전 예산 예약액을 다시 설계·평가해야 한다. 후보를 근거 없이 줄이면 정답 유형을 빠뜨릴 수 있고, 상한만 늘리면 월 비용 보호와 처리량 가정이 바뀐다. 어느 쪽이든 개발용·최종 평가를 통과하기 전에는 출시하지 않는다.

별개로, AI가 연결할 **사용자의 기존 구매 목적**을 저장·조회하는 DB 구조가 아직 없다. 목적 이름 없이 ID만 보내거나 임의의 목적을 만들게 할 수는 없으므로, 목적 데이터 모델과 조회 규칙을 구현하기 전에는 목적 연결까지 완료된 Worker로 간주하지 않는다.

## 해소 순서

1. 실제 출시용 모델 snapshot·출력 schema·상품 정보·87개 taxonomy와 최대 10개 목적의 대표 요청을 만든다. OpenAI의 입력 token 계산 API로 각 요청의 전체 token 수를 측정한다. 목적 데이터가 아직 없으므로 이 단계에서는 검증용 가상 목적 이름을 사용한다. 900바이트 guard는 정확한 token 상한이 아니므로 출시 기준으로 삼지 않는다.
2. 1,000 token 이내라면 과도한 900바이트 guard를 실제 token 검증으로 대체하고, 결과를 호출 전 예산 예약·실제 사용량 정산과 대조한다. 비용 산정에 token 계산 호출 자체가 포함되는지도 출시 전에 확인한다.
3. 넘는다면 먼저 중복 설명과 불필요한 상품 설명을 줄여 다시 측정한다. 그래도 넘으면 상품 정보로 후보를 사전 선택하되, 정답 유형이 후보에서 빠지는 비율을 개발 사례에서 먼저 측정한다. 후보에 정답이 없을 때는 임의의 다른 유형을 선택하지 않고 분류 보류로 처리한다. 정확도 기준을 통과하지 못하면 1,000 token 상향과 예산·처리량 재평가를 별도 결정한다.
4. 목적 연결은 사용자별 활성 목적의 ID·이름·설명·갱신 시각을 저장하고 최근 활성 목적 최대 10개를 읽는 구조를 마련한 뒤, 소유자와 삭제·변경 상태를 결과 반영 시 다시 검증한다. 이 구조가 없으면 목적 연결을 성공 처리하지 않는다.

즉, **측정 → 불필요한 입력 축소 → 필요할 때 후보 사전 선택 평가 → 그래도 실패하면 상한·비용 재결정**의 순서다. 분류 품질은 개발 사례로 조정하고, 봉인된 최종 평가 사례는 마지막 출시 판정에만 사용한다.
