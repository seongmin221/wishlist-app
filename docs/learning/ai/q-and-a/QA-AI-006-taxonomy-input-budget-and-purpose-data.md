# AI 분류 후보를 모두 보낼 수 없는 이유는 무엇인가

## 질문

공용 상품 유형 87개가 있는데 왜 AI Worker를 바로 켤 수 없으며, 입력 상한과 사용자 목적 데이터는 어떤 관계인가?

## 답변

AI가 상품을 분류하려면 상품 설명과 함께 **선택 가능한 유형의 ID와 이름**을 받아야 한다. `C026`이라는 ID만 보내면 모델은 이것이 `헤드폰`인지 알기 어렵다. 프로젝트에는 확정된 공용 유형 87개가 있고, 현재 이 ID·그룹·이름을 버전 데이터로 보관한다.

문제는 비용 보호를 위해 합의한 **호출당 입력 최대 1,000 token**과 현재 코드의 **요청 전체 최대 900 UTF-8바이트**가 서로 다른 단위라는 점이다. 900바이트는 실제 token 수를 세는 기능이 아니라 과다 입력을 막기 위한 매우 보수적인 임시 guard다. 87개 ID·그룹·이름만 간단히 이어도 약 3,845바이트라 이 guard에는 들어가지 않는다. 그렇다고 3,845바이트가 곧 3,845 token이라는 뜻은 아니다. 정확한 token 수는 모델과 요청 구조·출력 schema에 따라 달라지며, OpenAI는 실제 Responses 요청과 같은 형식으로 입력 token을 세는 API를 제공한다.

따라서 전체 후보를 그대로 보내려면 실제 요청의 token 수를 측정하고, 1,000 token 안에 들어가는지 확인해야 한다. 초과한다면 (1) 상품 정보로 후보를 먼저 좁히고 분류 정확도를 평가하거나, (2) 입력 상한과 호출 전 예산 예약액을 다시 설계·평가해야 한다. 후보를 근거 없이 줄이면 정답 유형을 빠뜨릴 수 있고, 상한만 늘리면 월 비용 보호와 처리량 가정이 바뀐다. 어느 쪽이든 개발용·최종 평가를 통과하기 전에는 출시하지 않는다.

별개로, AI가 연결할 **사용자의 기존 구매 목적**을 저장·조회하는 DB 구조가 아직 없다. 목적 이름 없이 ID만 보내거나 임의의 목적을 만들게 할 수는 없으므로, 목적 데이터 모델과 조회 규칙을 구현하기 전에는 목적 연결까지 완료된 Worker로 간주하지 않는다.

## 해소 순서

1. 실제 출시용 모델 snapshot·출력 schema·상품 정보·87개 taxonomy와 최대 10개 목적의 대표 요청을 만든다. OpenAI의 입력 token 계산 API로 각 요청의 전체 token 수를 측정한다. 목적 데이터가 아직 없으므로 이 단계에서는 검증용 가상 목적 이름을 사용한다. 900바이트 guard는 정확한 token 상한이 아니므로 출시 기준으로 삼지 않는다.
2. 1,000 token 이내라면 과도한 900바이트 guard를 실제 token 검증으로 대체하고, 결과를 호출 전 예산 예약·실제 사용량 정산과 대조한다. 비용 산정에 token 계산 호출 자체가 포함되는지도 출시 전에 확인한다.
3. 넘는다면 먼저 중복 설명과 불필요한 상품 설명을 줄여 다시 측정한다. 그래도 넘으면 상품 정보로 후보를 사전 선택하되, 정답 유형이 후보에서 빠지는 비율을 개발 사례에서 먼저 측정한다. 운영 중에는 사람의 정답을 알 수 없으므로 후보 누락 자체를 확정할 수 없다. 대신 후보 선정 근거가 부족하거나 안전한 후보 집합을 담지 못하면 임의의 유형으로 분류하지 않고 수동 분류로 남긴다. 정확도 기준을 통과하지 못하면 1,000 token 상향과 예산·처리량 재평가를 별도 결정한다.
4. 목적 연결은 사용자별 활성 목적의 ID·이름·설명·갱신 시각을 저장하고 최근 활성 목적 최대 10개를 읽는 구조를 마련한 뒤, 소유자와 삭제·변경 상태를 결과 반영 시 다시 검증한다. 이 구조가 없으면 목적 연결을 성공 처리하지 않는다.

즉, **측정 → 불필요한 입력 축소 → 필요할 때 후보 사전 선택 평가 → 그래도 실패하면 상한·비용 재결정**의 순서다. 분류 품질은 개발 사례로 조정하고, 봉인된 최종 평가 사례는 마지막 출시 판정에만 사용한다.

## 실제 측정 방법

1. 현재 Worker의 요청 생성 코드를 재사용해 **실제로 보낼 입력**을 만든다. 모델 snapshot, 상품 정보, taxonomy 87개, 목적 ID·이름 최대 10개, 지시문과 출력 JSON schema를 출시 후보와 동일하게 맞춘다. 목적 DB가 아직 없으므로 측정용 가상 목적을 쓰고 실제 사용자 정보나 API 키를 결과 파일에 남기지 않는다.
2. 짧은 상품 정보와 긴 상품 정보, 목적 0개와 10개를 조합해 최소 네 가지 사례를 만든다. 한국어·영어 이름과 설명이 긴 경계 사례도 넣는다. 이후 개발용 120개 사례가 준비되면 같은 방식으로 모두 측정한다.
3. 각 사례를 OpenAI의 `POST /v1/responses/input_tokens`에 보내 `input_tokens`를 기록한다. 출력 형식 등 계산 API가 수용하는 요청 항목은 실제 분류 요청과 같게 하고, 작은 개발 사례에서는 실제 Responses 응답의 `usage.input_tokens`와 대조해 누락된 항목이 없는지 확인한다. 계산 API의 과금 여부도 출시 전에 확인한다.
4. 중앙값·95백분위·최댓값과 **1,000 token 초과 건수**를 확인한다. 평균만 1,000 이하여서는 호출당 상한을 보장할 수 없다. 한 건이라도 초과하면 입력 축소 또는 후보 사전 선택 후 다시 측정한다. 출시 시에는 초과 요청을 분류 API로 보내지 않도록 호출 전 검사와 예산 예약을 연결한다.

실제 snapshot이 확정되기 전 별칭 모델로 얻은 수치는 설계 탐색용일 뿐 출시 보증 수치가 아니다. 아래 탐색 결과도 최종 요청과 개발 사례를 확정한 뒤 다시 측정해야 한다.

### 간결한 후보 표기 추가 탐색

같은 별칭 모델과 출력 schema를 유지하고, 목적 10개를 짧은 가상 이름으로 표기했다. 그룹형은 상위 그룹 이름을 한 번씩만 적고 그 아래 `ID:유형명`을 나열한다. 평면형은 그룹 이름을 빼고 `ID:유형명`만 나열한다. 후보 60·40·20개는 **파일의 앞부분을 임의로 잘라 토큰 용량만 본 것**이며, 실제 사전 선택 방식이나 분류 정확도를 검증한 것이 아니다.

그룹형 87개의 짧은 사례는 1,000 token에 겨우 들어가지만 1 token 여유만 남는다. 긴 상품은 시험한 후보 수 중 20개일 때만 이 가상 사례에서 가까스로 들어갔다. 그룹 이름을 빼는 표기는 비용을 줄이지만 동명이거나 모호한 유형의 문맥을 잃을 수 있다. 따라서 **입력 표기 압축만으로 모든 상품의 1,000 token 보장은 불가능**하다. 상품 정보 길이 제한과 후보 사전 선택의 품질·비용을 개발 사례로 평가해야 하며, 출시 전에는 실제 snapshot으로 다시 측정해야 한다.

## 후보 사전 선택 품질은 어떻게 확인하는가

사람이 정답 category ID를 붙인 개발 사례마다 후보 선정기를 먼저 실행한다. **후보 정답 포함률**은 `정답 ID가 후보 목록에 남은 사례 수 / 정답 ID가 있는 사례 수`로 계산한다. 정답이 `ABSTAINED`인 사례는 이 분모에서 빼고 별도로 평가한다. 후보 목록에서 정답이 빠지면 그 뒤 AI가 허용된 ID만 답하더라도 그 사례를 정확히 맞힐 수 없으므로, 포함률은 최종 category 정확도의 상한이다. 전체 평균과 함께 11개 상위 그룹·짧은/긴 metadata별 결과, 후보 수, 1,000 token 초과율, 수동 분류 전환율을 본다. 그 뒤 동일한 개발 사례에서 실제 AI 분류의 category 정확도·abstain 품질도 확인해야 한다.

**현재 검증 상태:** 저장소에는 taxonomy `ai/taxonomy/v1.json`은 있지만, 사람의 정답이 붙은 `ai/evaluations/development.jsonl`과 봉인된 holdout은 아직 없다. 따라서 후보 정답 포함률이나 출시 정확도는 아직 계산할 수 없다. 앞의 20·40·60개 수치는 임의로 앞에서 자른 목록의 **토큰 용량 측정**일 뿐 품질 측정이 아니다. 먼저 180개 metadata snapshot을 수집·라벨링하고, 첫 후보/모델 실험 전에 60개 holdout을 분리·봉인한 뒤 120개 개발 사례만으로 후보 선정기를 비교해야 한다.

### 사용자 제공 URL 8개 파일럿

2026-09-23에 사용자 제공 URL 8개를 확인하고 `ai/evaluations/user-links-pilot-draft.jsonl`에 출처·측정에 사용한 상품 metadata·잠정 category ID를 기록했다. 2026-09-24에 사용자가 8건 모두의 라벨을 확인했다. 경계 사례는 CAYL 캡 `C011`, Mizuno 트레일 러닝화 `C006`, 포켓몬 TCG 팩 `C068`이다. 패션 상품이 7개인 편향된 개발용 사례이므로 최종 holdout에는 사용하지 않는다.

현재 출력 schema, `gpt-5.6-luna` 별칭, 간결한 그룹형 taxonomy 87개를 쓴 입력 token 계산 결과는 목적 0개에서 **932–944 token**, 가상 목적 10개에서 **1,007–1,019 token**이었다. 제목 위주의 짧은 입력만 사용했으므로 실제 긴 설명과 사용자 목적 이름을 포함하면 더 커질 수 있다. 현 900바이트 guard는 이 요청을 모두 차단하며, 측정 자체가 호출 가능성을 입증하지 않는다.

실제 Responses 분류는 첫 호출에서 `429 credit_balance_exhausted`로 거부되어 재시도하지 않았다. 따라서 **모델 예측, category 정확도, 후보 사전 선택의 정답 포함률은 아직 측정하지 못했다.** 후보 선정기는 구현·검증 전이며, 라벨을 직접 만든 같은 8개로 조정한 뒤 얻는 점수는 독립 평가가 아니다. 별도 키나 과금 우회 없이 잔액 문제가 해결된 뒤에만 모델 파일럿을 재개한다.

### 2026-09-24 재측정과 실제 분류 시도

사용자가 8건의 category 라벨을 모두 확인한 뒤, 현재 기기에 설정된 API 키로 같은 별칭 모델 `gpt-5.6-luna`와 출력 schema를 사용해 입력 token을 다시 측정했다. 목적 후보는 0개이며, 제목 중심 metadata와 taxonomy 87개를 `그룹명[ID:유형명,...]` 형식으로 보냈다. 입력 token 계산 API는 분류 요청의 입력·출력 schema와 같은 값을 받았고, 계산 API가 허용하지 않는 `store`, `max_output_tokens`, `reasoning` 옵션만 뺐다.

| 사례 | 001 | 002 | 003 | 004 | 005 | 006 | 007 | 008 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 입력 token | 925 | 933 | 927 | 936 | 926 | 928 | 926 | 932 |

8건 모두 이 **개발용 입력**에서는 1,000 token 이하였지만, 실제 사용자 목적 10개와 긴 상품 설명을 넣는 운영 요청의 상한 충족을 뜻하지 않는다. 첫 사례 `001`로 `POST /v1/responses` 분류를 한 번 시도했으나 HTTP 429, 오류 코드 `credit_balance_exhausted`가 반환됐다. 나머지 7건은 호출하지 않았다. 따라서 이번에도 예측·정확도·실제 응답 token 사용량은 없다. 후보 선정기를 사용하지 않았으므로 후보 정답 포함률 역시 미측정이다. API 크레딧이 복구된 후에만 재개한다.

### 2026-09-24 실제 분류 재시도

같은 API 키와 요청 형식으로 다시 시도하자 8건 모두 `completed` 응답을 받았다. 결과는 [`user-links-pilot-results-2026-09-24.jsonl`](../../../../ai/evaluations/user-links-pilot-results-2026-09-24.jsonl)에 기록했다. 확정 category 라벨과 모델 예측은 **8/8 일치**했고, 목적 후보가 없는 요청이므로 모두 `UNASSIGNED`였다. 실제 사용량은 입력 합계 7,433 token(건당 925–936), 출력 합계 272 token(건당 34)이었으며, 사전 입력 token 계산값과 실제 `usage.input_tokens`가 8건 모두 같았다.

이 결과는 전체 87개 taxonomy를 간결한 그룹형 표기로 넣고 짧은 제목 중심 metadata만 사용한 **개발용 파일럿**이다. 모델은 출시 snapshot이 아닌 `gpt-5.6-luna` 별칭이며, 목적 10개·긴 설명·후보 선정기를 검증하지 않았다. 동일한 8건을 라벨 검토와 요청 설계에 사용했고 패션 상품에 편향돼 있으므로 8/8 일치를 독립 정확도나 출시 품질로 해석하지 않는다. 이 호출은 900바이트 guard가 있는 현재 서버 adapter가 아니라 평가용 직접 API 요청이었으며, 서버 runtime의 분류 가능성을 검증한 것도 아니다.

## 추가 질문: 8건을 모두 맞혔는데 지금도 무엇이 문제인가

8건의 결과는 **간결한 평가용 요청에서는 카테고리 선택이 가능하다**는 작은 신호다. 현재 서버의 `OpenAiResponsesGateway`는 후보를 Kotlin의 `(ID, 이름)` 목록 문자열로 풀어 넣어 같은 87개도 짧은 상품에서 1,657 token이었다. 게다가 요청 전체가 900 UTF-8바이트를 넘으면 `input_too_large`로 호출 전 차단한다. 평가용 요청은 `그룹명[ID:유형명,...]`으로 압축해 이 guard를 거치지 않고 직접 API를 호출했다. 따라서 성공한 파일럿과 현재 서버의 실제 요청은 같은 경로가 아니다.

압축해도 여유가 작다. 이번 제목 중심 8건·목적 0개는 925–936 token이었지만, 앞선 가상 목적 10개 실측은 1,007–1,019 token으로 기본 1,000 token 제한을 넘었다. 긴 상품 설명은 더 커진다. 현재 서비스는 응답 후 사용량이 1,000/80 안인지 정산 시 검사하지만, 실제 token 수를 호출 **전에** 검사하지 않는다. 900바이트 guard만 제거하면 상한을 넘는 호출이 먼저 과금될 수 있다. 목적 후보 DB·공급과 출시 model snapshot도 아직 없어 목적 연결의 운영 경로를 검증하지 못했다.

**권장 해결 순서:**

1. 평가에서 검증한 간결한 taxonomy 표기와 상품 metadata 정규화·길이 제한을 서버의 단일 요청 생성 경로에 반영한다. 상품명·브랜드·상점 등 분류 근거를 우선하고, 장황한 설명은 의미를 잃지 않는 범위에서 제한한다. 평가 도구도 같은 요청 생성 코드를 사용하게 한다.
2. 서버에서 전송 전에 실제 요청과 출력 schema의 입력 token을 검사한다. OpenAI의 입력 token 계산 API는 Responses와 같은 형식의 입력을 계산하며, 이번 8건의 계산값은 실제 응답 사용량과 같았다. 계산 API의 과금·지연과 호출 실패 시 정책도 확인해 예산 예약에 포함한다. token 초과 요청은 호출하지 않고 수동 분류로 보낸다. 900바이트 guard는 이 검증이 자리 잡은 뒤 교체한다.
3. 목적 10개·긴 설명에서 계속 초과하면 category 후보 사전 선택을 개발 사례에서 평가한다. 정답 후보 포함률과 수동 분류율을 확인하고, 근거가 부족할 때는 억지로 좁히지 않는다. 그래도 품질·처리량을 충족하지 못하면 1,000 token 상향을 별도 비용 평가와 월 10,000원 hard cap 아래에서 검토한다.
4. 사용자 목적 데이터 모델과 최근 활성 목적 공급, 출시 snapshot 고정, 개발 120건·독립 holdout 60건 평가를 완료한다. 8건의 8/8은 이 평가를 대체하지 않는다.

## 추가 질문: 입력 상한을 1,500–2,000 token으로 늘리면 해결되는가

일부 요청의 **token 용량 문제는 완화**되지만 단독 해결책은 아니다. 기존 서버형 요청은 짧은 상품에서도 목적 0개 1,657 token, 목적 10개 1,866 token이므로 1,500으로는 부족하다. 2,000은 이 두 짧은 사례를 담지만 긴 상품의 2,317–2,526 token은 담지 못한다. 간결한 그룹형 요청은 짧은 상품·목적 10개가 1,007–1,019 token이므로 1,500에 들어가고, 측정한 긴 가상 상품은 1,659 token이라 2,000에 들어간다. 실제 목적명·설명 길이의 분포와 최댓값은 아직 측정하지 않았다. 상한을 올려도 현재 900바이트 guard는 요청을 막으며 목적 후보 공급·품질 평가 문제도 남는다.

비용도 별도 판단이 필요하다. `gpt-5.6-luna` 표준 단가(입력 $0.20/100만 token, 출력 $1.20/100만 token), 월 20,000건, 건당 출력 예약 상한 80 token, 모든 요청이 입력 상한을 끝까지 쓴다는 보수적 가정의 **모델 호출료**는 다음과 같다. cache 할인, 재시도, 입력 token 계산 호출의 과금 여부는 포함하지 않았다.

| 건당 입력 상한 | 월 모델 호출료 | 1달러=1,350원 예시 |
| ---: | ---: | ---: |
| 1,000 token | $5.92 | 약 7,992원 |
| 1,500 token | $7.92 | 약 10,692원 |
| 2,000 token | $9.92 | 약 13,392원 |

따라서 월 10,000원 hard cap과 월 20,000건을 **모든 건이 새 상한까지 쓰는 조건**으로 동시에 보장할 수는 없다. 반면 실제 입력이 파일럿처럼 대부분 1,000 token 안팎이고 긴 요청만 드물다면 더 높은 최대 상한을 두어도 평균 비용은 낮을 수 있다. 대안은 간결한 서버 요청을 먼저 구현하고, 같은 요청에 대해 호출 전 token 수를 확인한 뒤, 드문 긴 요청에만 1,500–2,000 token까지 허용하는 방식이다. 이는 현재 합의된 기본 상한 변경 제안이며 아직 채택된 정책이 아니다. 예산 reservation은 해당 호출의 허용 최대 입력과 출력 80 token을 반영해야 하며, 월 hard cap에 닿으면 추가 호출을 중단한다. 개발 corpus에서 길이 분포·초과율·품질·월 예상 처리 건수를 측정하고 후보 사전 선택 방안과 비교한 다음 상한 값을 결정한다.

초기 사용 범위는 개인 용도이므로 위의 월 20,000건 전량 사용 가정은 당장의 비용 예측이 아니다. 예를 들어 건당 입력 2,000·출력 80 token을 모두 쓰더라도 표준 모델 호출료는 100건에 $0.0496, 1,000건에 $0.496이다. 이는 입력 token 계산 호출·재시도 등을 제외한 최대 요청 사용량 예시이며, 실제 입력은 요청마다 다르다. 개인 단계에서는 2,000 token 상한을 유력한 시험안으로 두되, 간결한 서버 요청·900바이트 guard 교체·호출 전 token 검사·예산 예약 갱신 없이는 상한 숫자만 변경하지 않는다.

## 구현 확인 (2026-09-24)

이후 개인 사용 단계의 2,000/80 상한이 채택되어 서버에 반영됐다. 그룹형 taxonomy 요청, 호출 전 정확한 token 계산, 2,000 초과 전송 차단, 2,000/80 기준 예산 예약, 응답 usage 검증을 함께 적용했다. 일반 Worker 실행 역할에 전체 v1 taxonomy를 연결하고, 로컬 통합 테스트에서 상품 생성 API → Worker HTTP → fake OpenAI token/response HTTP → DB `READY`와 `C011` 저장을 확인했다. 추가 opt-in smoke test에서 같은 로컬 HTTP·DB 경로로 실제 OpenAI token/response API를 호출해 `CAYL cap → C011`, `READY`도 확인했다. 상품 metadata 추출은 fixture이므로 실제 URL 추출, 배포된 모바일 앱, 목적 후보, browser Worker와 Cloud Tasks IAM은 검증 범위 밖이다. 앞 절의 “아직 채택되지 않음”, “900바이트 guard가 남아 있음”, “Worker runtime 미연결”은 변경 전 진단이다.
