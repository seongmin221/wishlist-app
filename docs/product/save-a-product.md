# 상품 저장

> 상태: **제안** · 최종 갱신: 2026-09-10 · 관련 흐름: URL 공유부터 분석·복구까지

## 사용자 목표

브라우저나 지원 앱에서 발견한 상품 URL을 공유한 즉시 잃지 않고 보관하고, 분석 결과를 기다리지 않아도 위시리스트에 저장한다.

## 제품 원칙

- 신뢰할 수 있는 URL 수신·보관을 분석보다 먼저 한다. URL 저장 요청은 상품 분석이 끝날 때까지 기다리지 않는다.
- 로그인·네트워크 상태가 일시적으로 맞지 않아도 저장 의도와 계정 귀속을 잃지 않는다.
- 공용 캐시는 새 저장을 빠르게 만들기 위한 것이며, 사용자 항목이나 과거 항목을 자동으로 갱신하는 원본이 아니다.

## 범위

이 문서는 시스템 공유 수신, 로컬 대기, 서버 생성·분석, 캐시 재사용, 분석 실패의 재시도, 처리 중 삭제를 소유한다. 공통 용어는 [상품 상태 용어](references/item-states.md)를 따른다.

중복 후보의 탐지는 저장 과정에서 시작할 수 있지만, 후보 비교와 사용자의 삭제·유지 선택은 [구매 후보 정리의 중복 후보 비교와 정리](organize-candidates.md#중복-후보-비교와-정리)가 소유한다. 직접 정보 보완과 이후 편집은 [상품 확인과 편집의 상품 정보 편집](inspect-and-edit-a-product.md#상품-정보-편집)이 소유한다.

## 사용자 흐름

### 1. 공유 수신과 로컬 보관

사용자가 시스템 공유 시트에서 앱을 선택하면 공유 시트는 닫히고, 앱은 수신한 URL을 먼저 로컬에 보관한다. 로그인·네트워크 조건이 아직 충족되지 않아도 이 수신과 보관은 완료한다.

### 2. 로그인·오프라인 대기와 계정 귀속

로그인하지 않았거나 네트워크를 사용할 수 없으면 서버 저장·분석을 요청하지 않고 URL을 `로컬 대기`로 둔다. 로컬 대기 항목은 서버 전송에 성공하거나 사용자가 삭제할 때까지 자동 만료 없이 유지하며, 앱 종료와 기기 재부팅 뒤에도 남는다.

서버 전송 전 항목은 해당 기기에만 존재하므로 다른 기기에서 조회할 수 없다. 앱을 삭제하면 로컬 대기 URL도 삭제되고 재설치 후 복구하지 않는다. 최초 앱 진입에서는 로그인을 요구하되 건너뛸 수 있으며, 비로그인 홈은 로컬 저장 항목, 로그인하면 분석과 기기 간 이용이 가능하다는 안내, 로그인 진입점을 제공한다.

비로그인 상태에서 저장한 로컬 대기 URL은 이후 로그인한 계정의 서버 항목으로 생성한다. 반면 로그인한 채 오프라인으로 저장한 URL은 저장 당시 계정에 귀속한다. 다른 계정으로 로그인하면 그 대기 항목을 이전하거나 노출하지 않고, 원래 계정으로 다시 로그인했을 때만 전송을 재개한다.

### 3. 전송, 생성, 분석

로그인 뒤에는 비로그인 때 쌓인 대기 항목 전체를 자동으로 분석 요청한다. 항목별 `PROCESSING` 진행 상태를 표시하고 일괄 시작 알림은 제공하지 않는다. 앱 실행 중 네트워크가 복구되어도 대기 항목을 자동 요청한다. 앱이 꺼져 복구를 감지하지 못했으면 사용자가 UI에서 직접 분석을 요청할 수 있다.

로그인 상태에서 서버 저장·분석을 요청한 항목은 그 계정에 귀속한다. 로그아웃 뒤 다른 계정으로 로그인해도 기존 계정의 작업이나 결과는 새 계정에 이전·노출하지 않는다. 서버는 새 사용자 항목을 만들고, 추가 추출이 필요하면 대상 항목만 비동기로 분석한다. 서버 생성 뒤 항목은 기기 간에 조회할 수 있다.

## 상태와 전환

`로컬 대기`와 `PROCESSING`, `READY`, `PARTIAL`, `FAILED`, `재시도 가능`의 공통 의미는 [상품 상태 용어](references/item-states.md)에 둔다. 이 흐름에서는 로컬 대기가 전송 성공 후 서버 항목의 `PROCESSING` 또는 캐시로 생성된 항목으로 이어지고, 분석 결과는 `READY`, `PARTIAL`, `FAILED` 또는 `재시도 가능`으로 나타난다.

분석 중인 항목은 수정하거나 재추출할 수 없고 삭제만 할 수 있다. `PARTIAL` 또는 추출할 수 없는 결과는 누락·실패 사실을 별도로 알리며, 원본 링크 열기와 제품명·대표 이미지·카테고리 직접 입력을 제공한다. 직접 보완의 완료 조건과 편집의 상세 동선은 [상품 확인과 편집의 정보 보완 필요와 직접 보완 완료](inspect-and-edit-a-product.md#정보-보완-필요와-직접-보완-완료)에서 정한다.

## 캐시와 사용자 항목 경계

`Product`는 canonical URL과 서버가 추출한 재사용 가능한 metadata를 위한 공용 캐시다. MVP에서는 canonical URL이 같은 `READY` 캐시만 추출 완료 시점부터 7일 동안 새 저장에 재사용한다. `PARTIAL`과 `FAILED` 캐시는 재사용하지 않고, 새 저장 요청의 대상만 분석한다.

재사용 가능한 `Product`가 있으면 그 시점의 정보를 새 `WishlistItem`에 복사해 빠르게 생성한다. `WishlistItem`은 사용자별 표시용 정보와 수동 수정값을 보관하는 독립 snapshot이며, 복사 뒤 `Product`와 어느 방향으로도 동기화하지 않는다. 사용자가 제품명·대표 이미지 등을 수정해도 자신의 `WishlistItem`에만 반영되고 `Product`나 다른 사용자의 항목에는 반영하지 않는다.

`Product` 정보가 나중에 보완되거나 변경돼도 기존 `WishlistItem`은 갱신하지 않으며, 화면 조회 때 `Product` metadata를 실시간으로 읽지 않는다. 추출은 새 저장 요청의 대상만 처리하고 관련 상품이나 기존 `WishlistItem`을 연쇄 추출·갱신하지 않는다. MVP는 최초 추출 뒤 상품 정보 변화를 주기적으로 모니터링하거나 자동 갱신하지 않는다.

사용자가 공유한 원본 URL은 tracking parameter 등을 포함할 수 있다. 따라서 원본 URL은 사용자 `WishlistItem`의 경계에 두고 공용 `Product` 데이터로 무분별하게 공유하지 않는다.

## 예외와 복구

서버가 URL 분석을 시도한 뒤 실패하면 항목을 서버에 보존하고 `재시도 가능`으로 표시한다. 실패 원인을 기록하며, 사용자는 직접 보완하기 전까지 항목별로 분석을 다시 요청할 수 있다. 앱과 API는 네트워크 단절 중 저장 요청이 실패한 상태를 사용자에게 명확히 보인다.

분석 결과의 `PARTIAL`·`FAILED` 처리와 재시도는 새 요청의 대상 항목에만 적용한다. 중복 후보가 발견되어도 저장을 차단하거나 자동 병합하지 않는다. 추출 뒤 후보를 안내하는 시점과 사용자의 최종 정리 선택은 [구매 후보 정리의 중복 후보 비교와 정리](organize-candidates.md#중복-후보-비교와-정리)의 범위다.

## 삭제와 늦게 도착한 결과

분석 중인 항목을 삭제하면 목록에서 즉시 제거한다. 진행 중인 서버 작업은 가능한 경우 중단하지만, 중단하지 못해 결과가 늦게 도착해도 삭제된 항목에 결과를 반영하거나 항목을 자동 복원하지 않는다.

삭제한 상품과 같은 URL을 다시 공유하면 이전 항목을 복원하지 않고 새로운 항목으로 처리한다. 이 규칙은 처리 중 삭제와 늦은 완료 결과의 경합에도 동일하게 적용한다.

## 기술 경계

URL 정규화, SSRF 검증, fetch, parser와 렌더링 사용 기준은 [상품 정보 추출 pipeline](../architecture/server/extraction-pipeline.md)이 소유한다. 이 흐름은 사용자에게 보이는 저장·대기·복구 규칙만 소유하며 API, queue, 데이터베이스의 구현 상세를 정하지 않는다.

## 미결정 사항

- URL 저장 요청이 분석 완료를 기다리지 않는 규칙, 원본 URL의 공용 캐시 공유 제한, 네트워크 단절 중 실패 상태의 사용자 표시에는 아직 제안 근거가 남아 있다.
- 처리 완료 알림을 polling, realtime, push 중 무엇으로 제공할지는 서버 설계에서 아직 결정하지 않았다.
